# 排班管理与教练车车辆管理 — 评估与实现文档

## 一、背景与问题

当前系统中，教练通过 `PUT /coach-portal/available-time` 自由设置空闲时段（JSON 格式），学员据此约课。但这跳过了两个关键资源约束：

1. **车辆约束**：驾校教练车数量有限，不同车型（C1/C2/N1...）数量不同，同一台车不能同时被两个教练使用
2. **场地约束**：每个训练场地同时可容纳的教练车数量有限，且可能限制训练车型

因此需要在"教练设空闲时段"之前插入一层**资源申请与排班**流程：

```
教练申请车辆+场地+时段 → 管理员审核排班 → 审核通过后该时段自动成为教练可约课时段 → 学员约课
```

---

## 二、现有系统相关模块盘点

| 现有模块 | 与新功能的关系 | 需改动程度 |
|---------|--------------|-----------|
| `coach` 表 | `vehicle_type` 字段标记教练准教车型，排班时需校验车型匹配 | 无需改动 |
| `venue` 表 | `venue_type=2` 为训练场地，但缺少"可容纳车辆数""支持车型"等字段 | **需加字段** |
| `appointment` 表 | 约课应约束在已批准的排班时段内 | **需加 schedule_id 外键** |
| `coach.available_time` JSON | 将被排班模块替代为派生数据 | **逻辑变更** |
| `coach_application` 表 | 学员申请教练的审核流，可作为排班审核的参考模式 | 参考，不改 |
| `fee_standard` 表 | 车辆使用可能涉及费用（如教练车使用费） | 可选扩展 |

## 三、数据模型设计

### 3.1 新表：`vehicle`（教练车）

```sql
CREATE TABLE vehicle (
    id              INT UNSIGNED AUTO_INCREMENT COMMENT '车辆ID',
    plate_number    VARCHAR(20)  NOT NULL COMMENT '车牌号',
    vehicle_type    VARCHAR(10)  NOT NULL COMMENT '车型: C1/C2/B1/N1...',
    brand           VARCHAR(50)  DEFAULT NULL COMMENT '品牌',
    model           VARCHAR(50)  DEFAULT NULL COMMENT '型号',
    seats           TINYINT      DEFAULT 5 COMMENT '座位数/核载人数',
    status          TINYINT      NOT NULL DEFAULT 1 COMMENT '1-空闲, 2-使用中, 3-维修, 4-报废',
    remarks         VARCHAR(200) DEFAULT NULL COMMENT '备注',
    create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_deleted      TINYINT(1)   NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    KEY idx_type (vehicle_type),
    KEY idx_status (status),
    KEY idx_is_deleted (is_deleted)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教练车表';
```

### 3.2 新表：`coach_schedule`（排班记录 / 车辆使用申请）

```sql
CREATE TABLE coach_schedule (
    id              INT UNSIGNED AUTO_INCREMENT COMMENT '排班ID',
    coach_id        INT UNSIGNED NOT NULL COMMENT '教练 coach_id',
    vehicle_id      INT UNSIGNED NOT NULL COMMENT '车辆ID',
    venue_id        INT UNSIGNED NOT NULL COMMENT '训练场地ID',
    license_type    VARCHAR(10)  NOT NULL COMMENT '培训车型（需与车辆车型匹配）',
    start_time      DATETIME     NOT NULL COMMENT '开始时间',
    end_time        DATETIME     NOT NULL COMMENT '结束时间',
    max_students    TINYINT      NOT NULL DEFAULT 1 COMMENT '该时段最大可容纳学员数（1对1或1对多）',
    booked_count    TINYINT      NOT NULL DEFAULT 0 COMMENT '已预约学员数',
    status          TINYINT      NOT NULL DEFAULT 0 COMMENT '0-待审核, 1-已通过, 2-已拒绝, 3-已完成, 4-已取消',
    apply_reason    VARCHAR(200) DEFAULT NULL COMMENT '申请说明',
    audit_remark    VARCHAR(200) DEFAULT NULL COMMENT '审核备注/拒绝原因',
    apply_time      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '申请时间',
    audit_time      DATETIME     DEFAULT NULL COMMENT '审核时间',
    create_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    is_deleted      TINYINT(1)   NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    KEY idx_coach (coach_id),
    KEY idx_vehicle (vehicle_id),
    KEY idx_venue (venue_id),
    KEY idx_time_range (start_time, end_time),
    KEY idx_status (status),
    KEY idx_is_deleted (is_deleted)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='教练排班/车辆使用申请表';
```

### 3.3 现有表改动

**`venue` 表 — 增加字段：**

```sql
ALTER TABLE venue
    ADD COLUMN max_vehicles       TINYINT UNSIGNED DEFAULT NULL COMMENT '最大同时容纳车辆数',
    ADD COLUMN supported_types    VARCHAR(50)      DEFAULT NULL COMMENT '支持训练的车型，逗号分隔，NULL表示不限';
```

**`appointment` 表 — 增加外键（可选，渐进式改造）：**

```sql
ALTER TABLE appointment
    ADD COLUMN schedule_id INT UNSIGNED DEFAULT NULL COMMENT '关联排班ID',
    ADD KEY idx_schedule (schedule_id);
```

> 加此字段后，约课被约束在已批准的排班时段内。可渐进改造：先不加，排班模块独立运行后，再由约课模块引用。

## 四、业务流程设计

### 4.1 教练申请排班（核心流程）

```
教练端                                    管理员端
  │                                         │
  ├─ POST /coach-portal/schedules           │
  │  { vehicleId, venueId, startTime,       │
  │    endTime, licenseType, maxStudents }   │
  │                                         │
  │  ┌── 系统自动校验 ──────────────────┐    │
  │  │ 1. 教练准教车型是否包含 licenseType │    │
  │  │ 2. 车辆的 vehicle_type 是否匹配     │    │
  │  │ 3. 场地是否支持该车型               │    │
  │  │ 4. 该时段车辆是否已被占用           │    │
  │  │ 5. 该时段场地是否超出最大车辆数     │    │
  │  │ 6. 该时段教练是否已有其他排班       │    │
  │  │ 7. startTime < endTime 且在未来     │    │
  │  └──────────────────────────────────┘    │
  │                                         │
  │  状态: 0-待审核                         │
  │                                         │
  │                                         ├─ GET /admin/schedules/pending
  │                                         │  查看待审核排班列表
  │                                         │
  │                                         ├─ PUT /admin/schedules/{id}/audit
  │                                         │  status=1(通过) 或 2(拒绝)
  │                                         │  auditRemark=拒绝原因
  │                                         │
  │  ← 审核通过 → 该时段成为教练可约课时段 ──│
  │                                         │
  └─────────────────────────────────────────┘

学员端约课流程（仅可在自己教练的排班时段内约课）:

学员                                      系统
  │                                         │
  ├─ GET /schedules/available               │
  │  查询我的教练已批准的排班时段             │
  │                                         │
  │  ┌── 系统自动过滤 ──────────────────┐    │
  │  │ 1. 通过 student_coach 找到学员的    │    │
  │  │    绑定教练 coach_id                │    │
  │  │ 2. 查出该教练 status=1(已通过)的    │    │
  │  │    排班记录                          │    │
  │  │ 3. 过滤 start_time > NOW()          │    │
  │  │ 4. 过滤 booked_count < max_students │    │
  │  └──────────────────────────────────┘    │
  │                                         │
  ├─ POST /appointments                     │
  │  { scheduleId, startTime, endTime }     │
  │                                         │
  │  ┌── 约课时再次校验 ────────────────┐    │
  │  │ 1. 该排班是否属于学员的绑定教练     │    │
  │  │ 2. 该排班是否 status=1(已通过)     │    │
  │  │ 3. booked_count 是否未满           │    │
  │  │ 4. 约课时间是否在排班时段范围内     │    │
  │  │ 5. 学员是否已有冲突约课             │    │
  │  └──────────────────────────────────┘    │
  │                                         │
  │  约课成功 → schedule.booked_count + 1   │
  │                                         │
  │  [时段结束后 status → 3-已完成]         │
```

### 4.2 校验规则（分两阶段）

#### 阶段 A：排班申请时（教练 → 管理员审核）

| 校验项 | 检测条件 | 错误提示 |
|-------|---------|---------|
| **车型匹配（教练）** | 教练 `vehicle_type` 是否包含 `license_type` | "您的准教车型不包含该车型" |
| **车型匹配（车辆）** | 车辆 `vehicle_type` 是否等于 `license_type` | "该车辆不支持此车型培训" |
| **车型匹配（场地）** | 场地 `supported_types` 是否包含 `license_type`（若有限制） | "该场地不支持此车型培训" |
| **车辆冲突** | 同一 `vehicle_id` 同一时段已有已通过的排班 | "该车辆在此时段已被占用" |
| **场地超容** | 同一 `venue_id` 同一时段已通过排班数 ≥ `venue.max_vehicles` | "该场地在此时段已达到最大容纳车辆数" |
| **教练冲突** | 同一 `coach_id` 在同一时段已有已通过的排班 | "您在此时段已有其他排班" |
| **时间合法性** | `startTime < endTime` 且 `startTime > NOW()` | "时间范围不合法" |

#### 阶段 B：学员约课时（学员 → 仅可在自己教练的排班内约课）

| 校验项 | 检测条件 | 错误提示 |
|-------|---------|---------|
| **学员绑定教练** | 学员通过 `student_coach` 表查找绑定教练的 `coach_id` | "您还没有绑定教练，请先申请教练" |
| **排班归属** | 目标排班的 `coach_id` 必须等于学员的绑定教练 | "只能预约您教练的课程时段" |
| **排班状态** | 排班 `status = 1`（已通过） | "该时段不可约" |
| **名额未满** | 排班 `booked_count < max_students` | "该时段已约满" |
| **时段范围** | 约课的 `startTime`/`endTime` 必须在排班时段内 | "约课时间超出教练可用时段" |
| **学员时间冲突** | 学员在同一时段无其他已确认的约课 | "您在该时段已有其他约课" |
| **身份校验** | `studentId` 从 JWT 取，不从请求体取 | "无权操作" |

### 4.3 教练可用时段（替代 available_time JSON）

**旧逻辑**：教练手动写 JSON `{"monday":["09:00-12:00"]}` → 自由格式、无约束

**新逻辑**：教练可用时段 = 查询 `coach_schedule WHERE coach_id=X AND status=1 AND start_time > NOW()`

- `GET /coach-portal/available-time` → 改为从 `coach_schedule` 表派生，只读返回
- `PUT /coach-portal/available-time` → **废弃**（或保留作为额外备注，但不再作为约课依据）

| `PUT` | `/admin/schedules/{id}/audit` | 审核排班（通过/拒绝） | 管理员 |

### 5.4 可约时段查询（学员端）

> 学员只能查看自己绑定教练的可约时段，不允许跨教练查询。

| 方法 | 路径 | 说明 | 角色 |
|------|------|------|------|
| `GET` | `/schedules/available` | 查看我已绑定教练的可约时段（自动从 JWT 取 studentId，查 `student_coach` 获取 coachId，再查该教练已通过的排班） | 学员 |
| `GET` | `/schedules/available?licenseType=C1&date=2026-06-10` | 按车型+日期进一步筛选 | 学员 |

**接口行为**：
1. 从 JWT 获取当前学员的 `userId`
2. 查 `student_coach WHERE student_id=X AND status=1` → 获取 `coach_id`
3. 若无绑定教练，返回错误 "请先申请分配教练"
4. 查 `coach_schedule WHERE coach_id=Y AND status=1 AND start_time > NOW() AND booked_count < max_students`
5. 可选按 `licenseType`、日期范围进一步过滤
6. 返回列表，每条包含：排班ID、教练姓名、场地名称、车牌号、车型、时段、剩余名额

### 5.5 场地管理改动

| `PUT /venues/{id}` | 增加 `maxVehicles`、`supportedTypes` 字段的更新 |
| `GET /venues` | 返回数据中包含新增字段 |

## 六、与约课模块的集成方案

### 6.1 解决之前评估发现的约课问题

| 约课问题 | 排班模块如何解决 |
|---------|----------------|
| P0-1: 状态码不一致 | 排班审核流有明确的状态常量，不与约课混淆 |
| P0-2: 缺少"已完成"状态 | 排班有状态 3=已完成，时段结束后自动/手动流转 |
| P0-3: 学员约课可伪造身份 | 不改排班模块，但约课改造时从 JWT 取 studentId |
| P0-4: 创建约课零校验 | **排班模块从根本上解决**：约课只能选已批准的排班时段，车辆/场地/教练/时间的合法性由排班审核保证 |
| P1-5: 缺少完成操作 | 排班有完成状态，约课完成后回写排班的 `booked_count` |
| P1-7: 学员看不到教练空闲 | 学员通过 `GET /schedules/available?coachId=X` 查看教练已批准的可约时段 |

### 6.2 渐进式改造路径

**Phase 1（新建，不影响现有功能）：**
- 新建 `vehicle` 表 + CRUD
- 新建 `coach_schedule` 表 + 申请/审核流程
- 场地表加字段
- 此时排班模块独立运行，不影响现有约课

**Phase 2（打通）：**
- `GET /coach-portal/available-time` 改为从 `coach_schedule` 派生
- 学员端新增 `GET /schedules/available` 查看可约时段
- 学员约课时校验时段必须在已批准的排班内

**Phase 3（深度整合）：**
- `appointment` 表加 `schedule_id` 外键
- 约课自动扣减 `coach_schedule.booked_count`
- 约课完成自动回写排班状态

## 七、冲突检测实现要点

### 7.1 时间重叠判断（SQL 层面）

```sql
-- 检测同一车辆在目标时段内有无冲突排班
SELECT COUNT(*) FROM coach_schedule
WHERE vehicle_id = #{vehicleId}
  AND status = 1
  AND start_time < #{endTime}
  AND end_time > #{startTime}
  AND is_deleted = 0;
```

同样的模式用于场地容量检测和教练冲突检测。

### 7.2 场地容量检测

```sql
SELECT COUNT(*) FROM coach_schedule
WHERE venue_id = #{venueId}
  AND status = 1
  AND start_time < #{endTime}
  AND end_time > #{startTime}
  AND is_deleted = 0;
```

若 count ≥ `venue.max_vehicles`，则拒绝。

### 7.3 车型匹配链

```
教练准教车型(Coach.vehicleType) ⊇ licenseType
  ∧ 车辆车型(Vehicle.vehicleType) = licenseType
  ∧ 场地支持车型(Venue.supportedTypes) ⊇ licenseType（若配置了限制）
```

## 十、风险与决策点

### 需要确认的设计决策

1. **排班粒度**：以"每辆车每次"为单位（一个教练申请一台车）= 一个排班记录。如果教练一次申请多天的重复排班（如"每周一到周五上午"），是提交一条记录还是多条？
   - 建议：**单条记录 = 单次时段**。重复排班由前端多次调用或增加批量申请接口。

2. **学员预约与排班的关系**：一个排班时段允许多少学员约课？
   - `max_students` 字段控制，教练申请时指定。默认为 1（一对一教学），可设为 2-4（小组教学）。

3. **车辆使用费**：教练使用教练车是否需要缴费？
   - 当前费用系统（`fee_standard`）可以扩展，但建议先不做，保持简单。

4. **场地 `max_vehicles` 粒度**：是否需要分时段限制（如上午 10 台、下午 8 台）？
   - 建议初版用一个固定值，后续可扩展为分时段配置表。

### 与约课问题的联动节奏

建议的修复顺序：
1. **先修约课 P0 的 Bug**（状态码、身份伪造、Service 层死代码）
2. **再上排班+车辆管理 Phase 1**（独立模块，不影响现有功能）
3. **最后 Phase 2-3 打通**（排班约束约课，形成完整闭环）

## 十一、总结

| 维度 | 评估 |
|------|------|
| **技术可行性** | 高。现有架构（MyBatis-Plus + 三层架构 + 审核流模式）完全支持 |
| **对现有系统影响** | 低。Phase 1 完全独立，Phase 2 仅改 available-time 的数据源 |
| **解决的问题** | 根本性解决约课缺乏资源约束的问题（车辆冲突、场地超容、教练时间冲突） |
| **工作量** | 约 8-10 小时（12 个新文件 + 5 个修改 + 1 个 SQL 脚本） |
| **主要风险** | 排班粒度的业务定义需确认；教练同时申请多条排班的 UI 复杂度 |
